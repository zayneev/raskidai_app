# Раскидай — план Telegram Mini App

Статус: прототип этапа 2 сохранён как демо. Подготовлены Telegram-авторизация, серверный API, миграция Supabase, приглашения и совместные расходы этапа 3; локальные и SQL-проверки пройдены. Проекты Supabase и Vercel созданы, приложение опубликовано на Vercel, Production открыт для Telegram, Preview защищён. Секреты бота и Supabase добавлены в Production и включены в новый деплой. Для пробного запуска с двумя аккаунтами остаются настройка Main Mini App и проверка с реальных устройств. Инструкция и переменные окружения — в [README.md](README.md).

## 1. Подтверждённые требования

- Название приложения — «Раскидай».
- Язык интерфейса первой версии — русский.
- Референс — Tricount, приложение для совместных расходов и расчёта долгов.
- Приложение открывается внутри Telegram и автоматически определяет пользователя по его Telegram-аккаунту.
- Группы и операции сохраняются на сервере и доступны при следующем открытии и на другом устройстве.
- Первая аудитория — автор проекта и его друзья. Архитектура должна позволять открыть сервис другим пользователям.
- Основной сценарий — мероприятия с друзьями, включая поездки и другие события.
- В первой версии нужна запись расходов при потере интернета с последующей синхронизацией.
- В первой версии фотографии чеков не нужны: достаточно суммы и описания расхода.
- В первой версии у каждого расхода один плательщик.
- Новый расход можно записать только как оплаченный самим авторизованным пользователем; выбрать другого плательщика нельзя.
- В первой версии нужны три способа распределения: поровну, по процентам и точным суммам, между выбранными участниками.
- В первой версии нужны категории расходов: жильё, транспорт, еда, развлечения и другое. Сводка мероприятия показывает суммы по категориям.
- В первой версии достаточно сводки внутри приложения; экспорт в файл отложен.
- В первой версии уведомления от бота не нужны; события видны внутри Mini App.
- В первой версии два типа операций: расходы и погашения долгов. Учёт возвратов за покупки и общих поступлений отложен.
- Первая валюта — RUB. Добавление других валют должно быть возможно позже.
- Приложение рассчитывает долги и фиксирует возврат денег.
- Отметить погашение может только отправитель или получатель соответствующего перевода; остальным участникам он доступен для просмотра.
- Интерфейс рассчитан прежде всего на телефоны: понятная навигация, плавные анимации, удобный ввод суммы.
- Для дизайна используем рекомендации официального frontend-design от Anthropic.
- Предпочтительные платформы: Vercel для приложения и Supabase для хранения данных.
- Пользователь подтвердил наличие Telegram-бота и аккаунтов Vercel и Supabase; конкретные проекты выбираем при подключении.
- Все участники должны войти через Telegram. Участники только по имени не нужны.
- Редактирование и удаление доступны автору записи и владельцу группы. Сохраняем историю изменений.
- Визуальное направление — Telegram и iOS со своим оформлением.

## 2. Предлагаемая архитектура

Telegram → интерфейс React / Next.js → серверный API Next.js на Vercel → PostgreSQL в Supabase.

### Интерфейс

TypeScript, React и Next.js. Стили — CSS с общей системой цветов, размеров, шрифтов и компонентов. Анимации взаимодействий — CSS и Motion for React по необходимости.

Предлагаем Next.js App Router с интерактивным клиентским интерфейсом: Telegram передаёт данные запуска в браузере, а локальная очередь расходов должна работать при потере сети. Для проверки авторизации, чтения данных и отправки очереди используем Route Handlers с Node.js runtime. Постоянный контракт API упрощает повторную отправку офлайн-записей. Персональные ответы API не попадают в общий кеш.

Интеграция с Telegram WebApp API: запуск, темы, кнопка «Назад», параметры высоты окна, безопасные отступы и тактильный отклик на поддерживаемых устройствах. Проверяем поведение клавиатуры, прокрутки и нижних панелей непосредственно в Telegram на iOS и Android.

### Авторизация

1. Mini App получает исходные данные запуска Telegram (`initData`).
2. Сервер проверяет их подпись и допустимый возраст.
3. По постоянному Telegram ID сервер находит пользователя или автоматически создаёт запись.
4. Сервер выдаёт ограниченную по времени сессию приложения.
5. Каждый запрос проверяет сессию и права пользователя на конкретную группу или операцию. При фиксации погашения сервер также проверяет, что пользователь — отправитель или получатель перевода.

Username и данные `initDataUnsafe` не используются как подтверждение личности. Токен бота и секреты базы хранятся на сервере.
При создании расхода сервер назначает плательщиком пользователя из проверенной сессии, не принимает идентификатор плательщика из запроса.

### Данные

PostgreSQL нужен для совместной работы и сохранения истории. Предлагаю первоначально проводить доступ к данным через серверный API. Сервер проверяет членство в группе и разрешения; прямой публичный доступ к таблицам приложения закрываем. Для таблиц в открытых схемах включаем RLS. Если появится доступ из клиента или Realtime, отдельно проектируем авторизацию подписок и политики доступа.

Основные сущности: пользователи, группы, членство в группах, приглашения, операции с одним плательщиком, доли участников, погашения и история изменений. Каждый участник связан с авторизованным Telegram-пользователем. Создатель группы приглашает друзей ссылкой; после входа и принятия приглашения они становятся участниками. Расход можно распределить на всех или на выбранную часть участников.

Фотографии чеков отложены; первая версия не требует Supabase Storage. Если позже добавим вложения, ограничим доступ участниками группы.

### Расчёты

- Рублёвые суммы храним целыми числами в копейках.
- Проверяем, что сумма долей соответствует сумме операции.
- Остаток при делении распределяем по определённому правилу: например, 100 ₽ на троих → 33,34 + 33,33 + 33,33 ₽.
- Баланс вычисляем из операций и погашений. Изменение или удаление операции вызывает пересчёт.
- Сумма балансов участников группы равна нулю.
- Предлагаем погашения, сокращающие количество переводов между участниками.
- Повторная отправка запроса не создаёт вторую операцию. Параллельное редактирование не должно незаметно затирать чужие изменения.
- В структуре операций предусматриваем код валюты. Правила пересчёта и хранения курсов проектируем при добавлении нескольких валют.

### Офлайн-запись в первой версии

Предлагаемая граница: запись новых расходов в уже загруженном приложении с ранее полученными данными группы. Первый вход, загрузка неизвестной группы и принятие приглашения требуют связи с сервером. Возможность повторного открытия Mini App без сети проверяем отдельно внутри Telegram на реальных устройствах.

Расход сначала сохраняется в локальной очереди с постоянным идентификатором и статусом «Ожидает синхронизации». После восстановления связи и проверки сессии очередь отправляется на сервер; повторные попытки не создают дубликатов. Несинхронизированные расходы обозначаются в списке и локальном предварительном балансе. При изменении прав или состава группы запись остаётся доступной локально и получает понятный статус, требующий решения пользователя.

Проверяем сохранность очереди после закрытия приложения, потерю сети во время отправки и повторный вход после истечения сессии.

## 3. Состав первой версии

### Основные сценарии

В интерфейсе группа соответствует отдельному мероприятию. Основные действия — быстро добавить расход, посмотреть расходы по датам и узнать, кто кому должен по этому мероприятию.

1. Открыть приложение и увидеть свои группы.
2. Создать группу: название, рублёвая валюта и создатель как первый участник.
3. Пригласить друга ссылкой в Telegram; он входит и присоединяется к группе.
4. Добавить свой расход: название, сумма, дата, категория и участники, между которыми делится расход.
5. Разделить расход поровну, по процентам или точным суммам.
6. Посмотреть список операций, сводку мероприятия и суммы по категориям, баланс каждого участника и предложения погашений.
7. Зафиксировать полный или частичный возврат долга.
8. Исправить или удалить запись с сохранением истории изменений.
9. Завершить мероприятие и перенести его в архив только после погашения всех долгов.

### Карта экранов

| Экран | Что делает пользователь |
| --- | --- |
| Мои мероприятия | Открывает мероприятие, создаёт новое, просматривает архив |
| Мероприятие | Переключается между расходами, балансами и сводкой |
| Добавление расхода | Вводит сумму и название, выбирает дату, категорию и участников; плательщик — он сам |
| Распределение суммы | Выбирает способ деления и проверяет итоговые суммы участников |
| Операция | Просматривает подробности и историю, исправляет или удаляет запись при наличии прав |
| Погашение | Выбирает отправителя и получателя, фиксирует сумму и дату возврата долга |
| Приглашение и участники | Вступает в мероприятие через Telegram, просматривает состав группы |

Сводка содержит общие расходы мероприятия, личную долю пользователя, суммы, оплаченные участниками, и расходы по категориям. Балансы показывают текущие долги с учётом погашений. Для несинхронизированных записей показываем статус и предварительные локальные итоги.

### Отложено по ответам пользователя

- Фотографии чеков.
- Несколько плательщиков у одного расхода.
- Уведомления через бота.
- Возвраты за покупки и общие поступления.
- Экспорт в файл.
- Несколько валют.

Дополнительные заметки, калькулятор при вводе суммы и расширенная статистика могут быть рассмотрены после пробного использования. Они не являются обязательными для первого запуска.

## 4. Этапы работы

### Этап 1. Спецификация поведения

На основе подтверждённых требований описать правила распределения, погашений, прав доступа и синхронизации. Подготовить конкретные примеры расчётов. При наличии скриншотов используемой версии Tricount сверить ключевые сценарии с референсом.

До полноценной сборки интерфейса выполнить небольшой технический эксперимент внутри Telegram на iOS и Android: сохранение локальной очереди, восстановление после закрытия, повторная отправка и работа в загруженной группе без сети. Это определит проверенные границы офлайн-режима.

Результат: таблица функций, правила расчётов, карта экранов и согласованные примеры поведения.

### Этап 2. Дизайн и интерактивный прототип

Разработать оформление в духе Telegram и iOS по референсу и ответам пользователя. Создать систему компонентов и прототип ключевого пути: открыть → создать группу → добавить расход → увидеть баланс → отметить погашение. Предусмотреть состояния загрузки, пустых списков, ошибок, длинных имён и больших сумм. Анимации должны показывать результат действия, а не мешать вводу.

Результат: прототип основных экранов на мобильной ширине. Предлагаем светлую и тёмную темы с учётом темы Telegram.

### Этап 3. Telegram, база и серверная логика

Настроить бота и запуск Mini App, проверку Telegram-авторизации, сессии, схему базы, миграции, права доступа и приглашения. Реализовать расчёты независимо от интерфейса и проверить их на конкретных сценариях.

Результат: работающая авторизация и серверное хранение с корректными расчётами и разграничением доступа.

### Этап 4. Работающее приложение

Связать прототип с API: группы, категории, операции, все четыре способа распределения, балансы, погашения, сводка, архив и история. Реализовать локальное хранение и очередь синхронизации расходов. Обеспечить обновление данных после изменений и возврата в приложение; механизм более частых обновлений выбрать по требованиям к совместной работе.

Результат: полный пользовательский путь с настоящими данными для нескольких Telegram-аккаунтов.

### Этап 5. Проверка в Telegram

Проверить iOS и Android, открытие приглашений, повторный запуск, работу с двух устройств, клавиатуру, темы и плавность интерфейса. Проверить округление, частичные погашения, удаление и исправление операций, повторные запросы, одновременные изменения и запрет доступа посторонних.

Результат: пройденные критерии ниже и исправленные ошибки.

### Этап 6. Публикация и пробное использование

Настроить Vercel, Supabase и публичный HTTPS-адрес Mini App, окружения для проверки и основного использования, секреты, журнал ошибок и восстановление данных в соответствии с выбранным тарифом. Подключить Mini App к боту и провести пробный запуск с друзьями.

Результат: доступное приложение внутри Telegram и список улучшений по реальному использованию.

## 5. Критерии готовности

- При открытии из Telegram пользователь попадает в свой аккаунт без ручной регистрации.
- После закрытия и повторного открытия данные сохранены; на другом устройстве доступны те же группы.
- Новый расход можно записать при потере связи в уже загруженной группе. После восстановления сети он появляется на сервере без дублирования.
- Локальная очередь сохраняется при закрытии приложения; несинхронизированные записи явно обозначены в интерфейсе.
- Друг входит по приглашению и видит общие операции.
- Балансы совпадают с согласованными примерами; копейки не теряются при делении.
- Погашение долга корректно меняет баланс.
- Редактирование и удаление доступны автору записи и владельцу группы и отражены в истории.
- Посторонний пользователь не может читать или менять группу, даже обращаясь напрямую к API.
- Интерфейс удобно работает внутри Telegram на iOS и Android.

## 6. Подготовка к подключению существующих ресурсов

Для текущего плана ответов достаточно. На этапе реализации:

1. Определить конкретного Telegram-бота и целевые проекты Vercel и Supabase.
2. Проверить, содержат ли выбранные проекты другие приложения или данные, и подготовить отдельное окружение для разработки.
3. Настроить серверные секреты в окружении приложения.
4. Перед публикацией выбрать production URL, тарифы, бюджет и порядок восстановления данных. Пользователь пока не сообщал о домене или бюджете.
