# Раскидай

Telegram Mini App для совместных расходов. Next.js 16, React 19, TypeScript. В браузере без Telegram открывается отдельный демо-режим с тестовыми данными; внутри Telegram после проверки подписи открываются общие серверные данные.

## Запуск

Нужны Node.js 24+ и pnpm 11.

```sh
pnpm install
pnpm dev
```

Открыть http://localhost:3000. На большом экране интерфейс сохраняет мобильную ширину 480 px.

В среде Codex, где Node.js доступен только в bundled runtime, можно использовать `./scripts/dev.sh`.

## Локальный Telegram WebApp SDK

Официальный SDK сохранён без изменений в `public/vendor/telegram-web-app.js`.
Источник и SHA-256 находятся в `src/lib/telegram-sdk-version.json`; хеш также
входит в URL скрипта, чтобы браузер получал новую копию после обновления.
При запуске приложение загружает SDK со своего домена. При сбое или таймауте
есть три попытки загрузки; «Попробовать снова» начинает новый цикл без
перезагрузки страницы. Вход по-прежнему использует серверную проверку `initData`.

```sh
pnpm telegram:sdk:check
pnpm telegram:sdk:update
```

Первая команда сравнивает копию с официальным источником, вторая подготавливает
обновление. Скачанный файл проверяется на структуру SDK и корректный синтаксис
JavaScript; HTML и ошибочные ответы не заменяют рабочую копию.

После слияния workflow `.github/workflows/telegram-sdk.yml` проверяет источник
каждый понедельник в 06:23 UTC; его также можно запустить вручную в GitHub Actions.
При изменении проходят проверка типов, тесты и сборка, затем предлагается draft PR
из ветки `automation/telegram-sdk`. Обновления нужно проверить в Telegram перед
слиянием. Автоматического слияния нет.

Для создания PR должен быть включён GitHub → Settings → Actions → General →
**Allow GitHub Actions to create and approve pull requests**. Если GitHub запрещает
создание PR, запуск сообщает об этом и сохраняет проверенный патч в артефакте
`telegram-sdk-update`. Ошибка получения официального файла также видна в Actions;
она не мешает запуску приложения с сохранённым SDK.

## Подключение реальных аккаунтов

Для реального режима нужны Supabase, Telegram-бот и опубликованный HTTPS-адрес приложения (например, Vercel). Проект `raskidai-dev` создан в Supabase (EU Central, Frankfurt); [миграция](supabase/migrations/20260929000000_shared_expenses.sql) применена через подключение Supabase. Миграция создаёт таблицы, RLS и атомарные функции. Роли `anon` и `authenticated` не получают доступ к этим таблицам и функциям; сервер использует `service_role`. Не применяйте миграцию к проекту с неизвестными приложениями без проверки существующей схемы.

Скопируйте `.env.example` в `.env.local` и заполните:

| Переменная | Что указать |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Токен бота от BotFather; только на сервере |
| `TELEGRAM_BOT_USERNAME` | Имя бота без `@` |
| `TELEGRAM_APP_SHORT_NAME` | Необязательно: короткое имя отдельного Direct Link Mini App; оставьте пустым для Main Mini App |
| `SUPABASE_URL` | `https://pyqdotllrvzypqwmpvow.supabase.co` |
| `SUPABASE_SECRET_KEY` | Серверный ключ `sb_secret_...` из Supabase → Settings → API Keys |
| `SUPABASE_SERVICE_ROLE_KEY` | Альтернатива: старый JWT-ключ `service_role` того же проекта |
| `APP_SESSION_SECRET` | Случайная строка от 32 символов; отдельная для каждого окружения |
| `APP_ORIGIN` | Точный origin приложения, например `https://app.example.com`; локально `http://localhost:3000` |

Для реального режима нужен **один** из ключей `SUPABASE_SECRET_KEY` или `SUPABASE_SERVICE_ROLE_KEY`; второй оставьте пустым. Также обязательны `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `SUPABASE_URL`, `APP_SESSION_SECRET` и `APP_ORIGIN`. Секреты задайте в серверном окружении Vercel, без префикса `NEXT_PUBLIC_`. Настройте у бота Main Mini App с HTTPS-адресом приложения через BotFather. Приглашение создаётся на 7 дней в формате `https://t.me/raskidai_app_bot?startapp=<token>`; Telegram передаёт токен в `start_param`. Если позже создадите отдельный Direct Link Mini App, задайте его `short_name` и ссылки станут `https://t.me/<bot>/<short_name>?startapp=<token>`. Приложение открывается в fullsize: `expand()` разворачивает окно по высоте, а верхняя панель Telegram остаётся видимой. Принудительный fullscreen не запрашивается; внутреннее название после загрузки скрывается. [Формат ссылки и проверка `initData` описаны Telegram](https://core.telegram.org/bots/webapps). [Новые ключи Supabase](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys) передаются через `apikey`, без JWT-заголовка.

Проект Vercel [`zayneev/raskidai-app-v2`](https://vercel.com/zayneev/raskidai-app-v2) создан и связан с этой директорией через `.vercel/project.json`. Production-сборка Next.js опубликована на `https://raskidai-app-v2.vercel.app`, и `APP_ORIGIN` задан тем же адресом без конечного `/`. В Production настроены `TELEGRAM_BOT_USERNAME`, `TELEGRAM_BOT_TOKEN`, `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `APP_SESSION_SECRET` и `APP_ORIGIN`. Токен бота, ключ Supabase и случайный секрет сессии сохранены как закрытые переменные Vercel; их значения не находятся в репозитории. После добавления двух секретов выполнено новое Production-развёртывание.

Production-адрес открыт для Telegram; Vercel Authentication сохранена для Preview-развёртываний. В [@BotFather](https://t.me/BotFather) откройте `/mybots` → `@raskidai_app_bot` → Bot Settings → Configure Mini App → Enable Mini App и задайте `https://raskidai-app-v2.vercel.app` как URL Main Mini App. `short_name` для этого не нужен. Затем откройте `https://t.me/raskidai_app_bot?startapp` из аккаунта А, создайте мероприятие и отправьте приглашение аккаунту Б. Исходный код хранится в [GitHub](https://github.com/zayneev/raskidai_app); первоначальная публикация на Vercel была сделана напрямую через CLI. Развёртывание имеет статус Ready; проверены HTTPS-ответ страницы `200`, отказ API без сессии `401` и отказ для поддельных Telegram initData `401`. Вход и совместная работа на двух реальных Telegram-аккаунтах пока не подтверждены.

После открытия Mini App клиент отправляет **сырой `initData`**, сервер проверяет HMAC и возраст (до часа), связывает Telegram ID с пользователем и выдаёт подписанную HttpOnly-сессию на 24 часа. Каждый запрос к API проверяет сессию, а SQL-функции проверяют участника или владельца мероприятия. `initDataUnsafe` не используется для личности. Ответы API не кешируются; интерфейс обновляется при возвращении и каждые 10 секунд во время просмотра.

Проверка с двумя аккаунтами: А создаёт мероприятие и через «Участники → Пригласить по ссылке» отправляет ссылку Б. Б открывает ссылку в Telegram; оба добавляют расходы и видят общие балансы. Должник нажимает «Я перевёл», получатель в своём аккаунте — «Я получил». До подтверждения баланс не меняется. Если получатель не ответил за 24 часа после отправки на подтверждение, перевод подтверждается автоматически и балансы пересчитываются. Посторонний пользователь не видит мероприятие в списке; запросы на изменение с его сессией отклоняются.

Автоподтверждение требует применения миграции [`20261031170439_auto_confirm_transfers.sql`](supabase/migrations/20261031170439_auto_confirm_transfers.sql). Она добавляет фоновую задачу Supabase `auto-confirm-transfers` через `pg_cron`, которая запускается раз в минуту даже при закрытом приложении. Срок отсчитывается от серверного `created_at`, а не от выбранной пользователем даты возврата; повторная отправка того же запроса не продлевает ожидание. Подтверждение происходит на первой проверке после истечения 24 часов; занятое мероприятие обрабатывается на следующем запуске. Уже просроченные переводы также обрабатываются после включения задачи. Ручное подтверждение и повторные запуски защищены от двойного учёта; в `change_history` и интерфейсе автоматическое подтверждение отмечается отдельно, без `confirmedBy` получателя. В демо тот же срок проверяется при открытии, возвращении в приложение и каждые 10 секунд; старые демо-записи без времени создания получают полные 24 часа с первого открытия после обновления. Миграция применена к удалённому `raskidai-dev` 31.10.2026. Проверены активное минутное расписание, успешный запуск `pg_cron`, автоматическое подтверждение одного ранее просроченного перевода и отсутствие публичного доступа к обработчику. Повторно применять SQL вручную к этому проекту не нужно.

Расходы и переводы отправляются с постоянными ID формы, поэтому повтор идентичного запроса не создаёт вторую запись. Редактирование и удаление расхода разрешены автору и владельцу мероприятия; версия расхода защищает от незаметной перезаписи. История хранится в `change_history`.

Создатель активного мероприятия может удалить участника через «Участники» → значок корзины → подтверждение. Сначала нужно погасить все долги участника и подтвердить его переводы. Создателя удалить нельзя. Удалённый участник теряет доступ и исключается из новых расходов; его имя, старые расходы и подтверждённые переводы сохраняются в истории. Расходы с удалённым участником доступны только для просмотра. Чтобы вернуть доступ и редактирование, создатель должен создать новое приглашение после удаления; старые ссылки не восстанавливают членство. Серверные изменения находятся в миграции `remove_event_participants`, SQL-проверка — в `tests/participants.sql` (с откатом тестовых данных).

Миграция [`20261001172950_remove_event_participants.sql`](supabase/migrations/20261001172950_remove_event_participants.sql) применена к Supabase `raskidai-dev` 01.10.2026. Проверка `tests/participants.sql` прошла в удалённой базе под ролью `service_role` с откатом тестовых данных: проверены права создателя, блокировка при долгах и ожидающих переводах, сохранение истории, отзыв доступа и повторный вход по новому приглашению. Публичные роли не имеют доступа к RPC удаления. Версия локального файла соответствует истории миграций Supabase.

## Что попробовать

1. Нажмите «Новое мероприятие» на главном экране.
2. Введите название, выберите символ мероприятия. В демо можно сразу добавить тестовых друзей; в реальном режиме пригласите их ссылкой после создания.
3. Добавьте расход: сумма, описание, категория, дата и выбранные участники. Новый расход всегда записывается как оплаченный вами; на его карточке рядом с вашим именем стоит «(Вы)».
4. Попробуйте деление поровну, по процентам или точным суммам.
5. Откройте «Балансы»: ваши переводы стоят первыми, рядом с вашим именем стоит «(Вы)». После «Я перевел» перевод получает статус «Ожидает подтверждения» и пока не меняет баланс. Когда получатель нажимает «Я получил» или истекают 24 часа ожидания, перевод подтверждается, статус исчезает, а балансы пересчитываются. Автоматическое подтверждение видно в «Погашениях» и «Активности». В браузерном демо шаг получателя можно воспроизвести через «Демо: подтвердить за получателя». Переводы между другими участниками видны ниже без действия погашения.
6. В «Сводке» верхняя плашка сравнивает общие расходы и вашу долю. Ниже «Мои расчёты» показывают, сколько вы оплатили, сколько вам вернули, сколько вернули вы и какой остаток нужно получить или вернуть. Ожидающие подтверждения переводы указаны отдельно и пока не входят в эти суммы. Дальше видно распределение по категориям.

Также работают редактирование и удаление расходов, история редактирования, добавление тестовых участников, архив мероприятий, активность и переключение темы. Завершить мероприятие можно после погашения всех долгов; при попытке завершить его приложение показывает предупреждение или подтверждение. В профиле можно восстановить исходные данные.

## Данные и границы прототипа

В демо изначально доступны три тестовых мероприятия и четыре вымышленных участника. После подтверждённого Telegram-входа интерфейс показывает реальные мероприятия и имена участников; рядом с текущим пользователем стоит «(Вы)». Демо-данные сохраняются в `localStorage` этого браузера под ключом `raskidai:prototype:v1`, тема — отдельно.

Расчёты выполняются в целых копейках. Остаток деления распределяется по наибольшим дробным остаткам с постоянным порядком при равенстве. Балансы учитывают расходы и подтверждённые погашения. Ожидающие переводы сохраняются, не предлагаются повторно и блокируют перенос мероприятия в архив.

В демо-режиме подтверждение вторым участником по-прежнему моделируется в одном браузере. Демо-данные сохраняются только в `localStorage`, отдельно от серверных мероприятий. Реальное погашение фиксирует сделанный перевод; деньги приложение не отправляет. Офлайн-очередь расходов для реального режима пока не реализована: добавление расхода требует соединения. Проверка на реальных iOS/Android и в выбранном Telegram-боте возможна после подключения окружения.

Подготовлены клиентские вызовы Telegram WebApp: ready, expand, тема, кнопка назад и тактильное подтверждение при запуске внутри Telegram. Проверка выполнена в Chromium на мобильных размерах; реальные iOS / Android и запуск в Telegram относятся к следующему этапу.

## Проверки

```sh
pnpm typecheck
pnpm test
pnpm build
```

SQL-проверки прав и расчётов находятся в `tests/shared.sql`. Их следует запускать в **одноразовой** PostgreSQL-базе после миграции с ролями Supabase; скрипт откатывает свои изменения. Он проверяет сценарий А/Б, запрет постороннему, права на правки, повторные операции, ожидание и подтверждение перевода, архив.

`tests/auto-confirm-transfers.sql` дополнительно проверяет расписание фоновой задачи, границу 24 часов, независимость от выбранной даты возврата, повтор запроса без продления срока, ручное и автоматическое подтверждения, историю, балансы и права доступа к фоновой функции. Для применения миграции локально нужен PostgreSQL с `pg_cron` в `shared_preload_libraries`; `cron.database_name` должен совпадать с именем тестовой базы.

В [VERIFICATION.md](VERIFICATION.md) — проверенный пользовательский сценарий и скриншоты. В [DESIGN.md](DESIGN.md) — визуальное направление на основе [официального frontend-design Anthropic](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md).

Интерфейс использует компактные символы мероприятий вместо фотографий обложек.
